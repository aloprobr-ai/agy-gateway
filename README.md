# Шлюз agy — OpenAI-совместимый API поверх Antigravity CLI

Маленький шлюз на PHP: снаружи он выглядит как OpenAI API, внутри отвечает
Google Gemini. Работает в Windows и в Linux, сторонних библиотек не требует —
нужен только PHP 8.1 или новее.

Два способа получить ответ:

| Режим | Как отвечает | Что нужно |
|---|---|---|
| `backend = 'cli'` | запускает Antigravity CLI (`agy`) и читает его поток событий | установленный и авторизованный `agy` |
| `backend = 'api'` | шлёт HTTP-запросы в Gemini | ключ из Google AI Studio |

В CLI-режиме ключи Gemini не нужны вовсе: шлюз работает через вашу учётную
запись Antigravity. Режим можно переключить и на один запрос — префиксом
модели: `"model": "cli/agy-pro"` или `"model": "api/gemini-2.5-flash"`.

Зачем это нужно: любая программа, умеющая говорить с OpenAI, начинает работать
с Gemini без единой правки — достаточно подменить адрес.

---

## Быстрый старт

Нужен PHP 8.1+ и, для CLI-режима, установленный и авторизованный `agy`.

### Windows

```powershell
copy config.example.php config.php
powershell -ExecutionPolicy Bypass -File bin\serve.ps1
```

PHP для Windows берётся с [windows.php.net](https://windows.php.net/download/)
(сборка **Non Thread Safe, x64**): распакуйте и добавьте папку с `php.exe`
в `PATH`.

### Linux, macOS

```sh
cp config.example.php config.php
chmod +x bin/serve.sh bin/agy-jail
./bin/serve.sh
```

PHP ставится пакетом: `sudo apt install php-cli php-curl php-mbstring`.

### Дальше — одинаково

Шлюз слушает `http://127.0.0.1:8080`. Проверить, что всё на месте:

```sh
php bin/doctor.php
```

Эта проверка не молчит: про каждую неполадку она пишет, чем именно её чинить.

Адрес для программ-клиентов — `http://127.0.0.1:8080/v1`. Ключ на своей машине
не нужен: пока `api_keys` в `config.php` пуст, шлюз пускает без ключа.

## Что умеет

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/v1/chat/completions` | чат; стриминг (SSE); картинки на вход; вызов инструментов; JSON-схемы |
| POST | `/v1/completions` | старый текстовый формат |
| POST | `/v1/embeddings` | эмбеддинги (нужен ключ Gemini) |
| POST | `/v1/images/generations` | нарисовать картинку |
| GET | `/v1/models`, `/v1/models/{id}` | список моделей |
| GET | `/health` | проверка живости, без ключа |
| GET | `/keys` | страница выдачи клиентских ключей (видна только со своего адреса) |

Сверх обычного OpenAI API:

- **Картинки на вход** — `image_url` в виде `data:image/...;base64,...` или
  http(s)-ссылкой (её скачает сам шлюз; частные адреса заблокированы, чтобы
  через него нельзя было постучаться во внутреннюю сеть).
- **Файлы от модели** — если модель за время ответа создала картинку или файл,
  шлюз положит его в раздачу и подставит в ответ ссылкой. Картинка приходит
  готовой разметкой `![имя](адрес)`.
- **Алиасы моделей** — `gpt-4o`, `gpt-4o-mini` и прочие сопоставлены моделям
  Gemini, чтобы работали программы с жёстко зашитыми именами.
- **Ротация ключей Gemini** — несколько ключей в конфиге; при `429` или `5xx`
  запрос автоматически повторяется со следующим.
- **Свои клиентские ключи** — `Authorization: Bearer sk-...`, с необязательным
  лимитом запросов в минуту.

│   ├── Compat.php          <- подпорки под отсутствующие расширения PHP

│   ├── agy-jail            <- песочница для CLI (Linux)
│   ├── doctor.php          <- проверка обстановки
│   ├── update.php          <- обновление самого шлюза из GitHub
│   └── update_models.php   <- обновление списка моделей

├── tests/
│   ├── smoke.php           <- проверка работающего шлюза

Код и `config.php` лежат **выше** корня сайта, поэтому по HTTP их не достать.

### Про пути в настройках

Почти все пути в `config.php` можно оставить пустыми: шлюз сам найдёт `agy`,
домашний каталог и место под файлы по правилам своей системы. Вписывать
вручную нужно только тогда, когда угадано не то, — и это как раз случай
веб-сервера: у PHP-FPM свой `PATH` и свой `HOME`, и `agy` из вашей консоли
там может не найтись.

Относительный путь в настройках считается от папки проекта, а не от текущего
каталога процесса: у шлюза он меняется на рабочий каталог беседы.

## CLI-режим

На каждый запрос шлюз запускает `agy -p "<промпт>" --output-format stream-json`
и читает поток событий: оттуда приходят идентификатор беседы, куски текста по
мере генерации и настоящий расход токенов.

Именно поток, а не файл транскрипта: в `transcript.jsonl` финальный текст может
не попасть вовсе — например, когда модель по дороге вызывала инструменты, там
остаются одни служебные записи.

Нужен `agy` не старее той версии, где появился `--output-format`. Если он
старый, шлюз так и скажет, а обновляется CLI сам: `agy update`.

### Размышления

Ход мысли модели в поток CLI не попадает — там только число потраченных на
него токенов. Зато в журнал беседы (`brain/<беседа>/.system_generated/logs/transcript_full.jsonl`)
каждый шаг ответа модели ложится с полем `thinking`: сжатым пересказом того,
о чём она думала, обычно по-английски и блоками с заголовком «**Что делаю**».
Шлюз читает журнал с того места, где остановился, и отдаёт эти мысли полем
`reasoning_content` — в потоке кадрами, в обычном ответе внутри `message`.

Шаг пишется в журнал, когда он закончен, поэтому мысли приходят по шагам, а не
по словам: у простого ответа — к концу, у работы с инструментами — перед
каждым действием. На совсем простых вопросах модель не думает вовсе, и
мыслей не будет. Прошлые ходы продолженной беседы не повторяются: чтение
начинается с конца журнала.

Там же, в `reasoning_content`, идут короткие строки о том, чем агент занят
(«Читаю файл», «Рисую картинку»), и раз в 15 секунд тишины — комментарий SSE
`: ping`, чтобы соединение не выглядело мёртвым.

### Как склеивается диалог

Беседа живёт внутри CLI, поэтому шлюз помнит, какой беседе соответствует какая
сессия клиента и сколько сообщений истории уже отправлено. Иначе на каждый
запрос пришлось бы пересылать всю переписку заново.

Сессию клиент задаёт заголовком `X-Session-Id`. Без него шлюз выводит
идентификатор из первого сообщения — работает, но хрупко: стоит клиенту начать
разговор с другой фразы, и это уже новая беседа.

### Рисование

`/v1/images/generations` работает в обоих режимах. По ключам это модель
Gemini Image, через CLI — его собственный инструмент рисования: шлюз просит
нарисовать и сохранить файлы, забирает их и отдаёт ответом.

`response_format` по умолчанию `b64_json` — тогда файл наружу не выкладывается
вовсе. При `url` картинка попадает в раздачу `/files/` и приходит настоящей
ссылкой, а не строкой `data:`.

Бэкенд выбирается как везде, так что префикс работает и тут: `api/gpt-image-1`
заставит пойти по ключам, `cli/` — рисовать через CLI.

Картинки, которые модель рисует сама по ходу разговора, приходят и в обычном
чате: шлюз подставляет их в конец ответа разметкой `![имя](ссылка)`.

### Чего CLI-режим не умеет

Эмбеддинги — на них нужен ключ Gemini в `config.php`. Всё остальное работает
одинаково в обоих режимах.

### Песочница

Шлюз запускает CLI с ключом `--dangerously-skip-permissions`. По-другому нельзя:
без него CLI на каждое действие ждёт подтверждения человека, а у HTTP-запроса
человека нет.

Но «не спрашивать» не должно означать «можно всё». В Linux запуск оборачивается
в `bin/agy-jail`: он заводит своё пространство монтирования и накрывает
системные каталоги (`/root`, `/www`, `/var`, `/etc/nginx` и прочие) пустыми
tmpfs только для чтения. Внутри они выглядят пустыми, снаружи не меняется
ничего — пространство исчезает вместе с процессом. Видимыми остаются дом CLI
и рабочий каталог беседы.

Нужен `unshare` из `util-linux` и разрешённые непривилегированные пространства
имён. Список каталогов меняется переменной `AGY_JAIL_HIDE`.

**В Windows песочницы нет.** Такого средства в системе просто не существует,
и притворяться, что защита есть, было бы хуже, чем её отсутствие: `/health`
и `bin/doctor.php` честно пишут `sandbox: unavailable`. Если изоляция важна —
заведите отдельную учётную запись Windows с урезанными правами и запускайте
шлюз от неё.

Песочницу можно потребовать жёстко: `'jail' => 'on'` в `config.php`. Тогда шлюз
откажется отвечать, если запереть CLI не удалось, — лучше честный отказ, чем
работа без защиты, на которую вы рассчитываете.

### Без учётной записи Antigravity

В `tests/fake_agy.php` лежит заглушка CLI: она говорит на том же языке, что
настоящий `agy`, но отвечает сама. Впишите в `config.php`:

```php
'command' => ['php', 'tests/fake_agy.php'],
```

— и весь шлюз можно проверить целиком, включая стриминг, картинки и вызов
инструментов. Удобно и для правок в самом шлюзе: не надо ждать настоящую модель.

## Обновление шлюза

```sh
php bin/update.php              # посмотреть, есть ли что нового
php bin/update.php --apply      # обновиться
php bin/update.php --force      # разложить файлы заново, если что-то испорчено
```

Если папка — клон git, обновление делается через `git pull --ff-only`: историю
видно, откатиться можно одной командой.

Если git недоступен (код сюда просто скопировали), скачивается срез
репозитория и раскладывается поверх. `config.php`, `storage`, `logs`
и `public/files` при этом не трогаются, а всё заменённое откладывается
в `storage/backups` — обновление, из которого нельзя вернуться, не обновление.
Ничего не удаляется: файл, исчезнувший в репозитории, останется лежать.

Запускать нужно от того же пользователя, от которого работает шлюз, иначе
обновлённые файлы окажутся чужими:

```sh
sudo -u www php bin/update.php --apply
```

После обновления шлюз надо перезапустить — PHP держит разобранный код в памяти,
и новый туда сам не попадёт. Скрипт напомнит, какой именно командой.

Пока репозиторий закрыт, GitHub отвечает `404` без ключа доступа. Ключ можно
положить в `update.token` или передать переменной окружения:

```sh
AGY_UPDATE_TOKEN=ghp_... php bin/update.php
```

## Постоянная работа

Встроенного сервера PHP хватает, когда шлюзом пользуетесь вы один. У него есть
особенность: **в Windows он обслуживает один запрос за раз**, и пока идёт
длинный ответ, вторая страница не откроется. В Linux `bin/serve.sh` поднимает
несколько обработчиков, и этой беды нет.

Если шлюз должен работать постоянно:

| Как | Что взять |
|---|---|
| Windows, автозапуск при входе | `powershell -File bin\install-task.ps1` |
| Linux, служба | `deploy/agy-gateway.service` |
| Linux, nginx + PHP-FPM | `deploy/nginx-site.conf` |
| aaPanel | `deploy/nginx-rewrite.conf` в «Псевдостатику» сайта |

Во всех случаях корнем сайта должна быть папка **`public`**, а не папка
проекта: иначе наружу окажутся видны `config.php` с ключами, `logs/` и
`storage/`.

Пользователь, от которого работает шлюз, должен быть тем же, под которым
авторизован `agy`: CLI берёт вход из домашнего каталога и от чужого имени
просто не войдёт. Под nginx это не вы, а `www` или `www-data`:

```sh
sudo -u www -H agy          # войти под пользователем шлюза
sudo -u www php bin/doctor.php
```

php bin/update_models.php
php bin/update_models.php --dry-run     # посмотреть, ничего не записывая

## Примеры

### Обычный запрос

```sh
curl http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "X-Session-Id: analytics-anna" \
  -d '{"model":"agy","messages":[{"role":"user","content":"Привет"}]}'
```

### Python

```python
from openai import OpenAI

client = OpenAI(api_key="не-важно", base_url="http://127.0.0.1:8080/v1")
answer = client.chat.completions.create(
    model="agy",
    messages=[{"role": "user", "content": "Привет"}],
)
print(answer.choices[0].message.content)
```

### Картинка на вход

```json
{"model": "agy", "messages": [{"role": "user", "content": [
  {"type": "text", "text": "Что на снимке?"},
  {"type": "image_url", "image_url": {"url": "data:image/png;base64,iVBORw0KGgo..."}}
]}]}
```

## Соответствие параметров

| OpenAI | Gemini |
|---|---|
| `temperature`, `top_p`, `top_k` | `temperature`, `topP`, `topK` |
| `max_tokens` / `max_completion_tokens` | `maxOutputTokens` |
| `stop` | `stopSequences` |
| `n` | `candidateCount` |
| `presence_penalty`, `frequency_penalty`, `seed` | одноимённые поля |
| `response_format` | `responseMimeType` + `responseSchema` |
| `tools` / `functions` | `functionDeclarations` |
| `tool_choice: required` | `functionCallingConfig.mode = ANY` |
| `reasoning_effort` | `thinkingConfig.thinkingBudget` |
| системные сообщения | `systemInstruction` |

`usage` возвращается настоящий; «думающие» токены учтены в `completion_tokens`
и продублированы в `completion_tokens_details.reasoning_tokens`.

## Безопасность

- Ключи лежат в `config.php` выше корня сайта и наружу не отдаются.
- Пока `api_keys` пуст, шлюз пускает **без ключа**. На своей машине это удобно,
  но наружу такой шлюз открывать нельзя: любой, кто до него достучится, получит
  и вашу учётную запись Antigravity, и право запускать CLI.
- В интернет — только через https. Ключ уходит в заголовке `Authorization`
  открытым текстом, и по http его прочитает любой на пути.
- `rate_limit_per_min` ограничивает частоту запросов по клиентскому ключу.
- `allow_remote_images: false` запрещает шлюзу ходить по присланным ссылкам
  вообще — тогда картинки принимаются только в base64.
- `log_bodies` по умолчанию выключен: тела запросов, а значит и переписка,
  в логи не пишутся.
- Про песочницу для CLI — см. выше. Без неё модель видит весь диск.

## Если что-то не работает

| Что видно | В чём дело |
|---|---|
| `404 Unknown endpoint` на `/v1/...` | все пути должны идти в `index.php`: не применён rewrite или корнем сайта выставлена не `public` |
| `401 Missing API key` при верном ключе | веб-сервер срезает заголовок `Authorization`; на Apache помогает правило из `public/.htaccess` |
| `500 config.php not found` | не скопирован `config.example.php` в `config.php` |
| `CLI backend requires proc_open()` | `proc_open` попал в `disable_functions` — уберите его в настройках PHP |
| `Antigravity CLI (agy) not found` | не найден ни в `PATH`, ни в привычных местах: впишите полный путь в `cli.command` |
| `CLI did not report a conversation id` | CLI не авторизован под пользователем шлюза, или он слишком старый (`agy update`). Подробности — в `logs/agy-stderr.log` |
| `Eligibility check failed ... not available in your location` | Antigravity не работает в вашей стране; пропишите прокси в `cli.env` |
| `CLI did not answer within Ns` | CLI молчал дольше `cli.timeout` — это предел тишины, а не всего ответа; весь ответ ограничен `cli.max_time` (840 с) |
| 504 от nginx на долгих ответах | `fastcgi_read_timeout` меньше `cli.max_time` — см. `deploy/nginx-site.conf` |
| 502 на долгих ответах, в журнале PHP-FPM `execution timed out` | `request_terminate_timeout` в пуле PHP-FPM меньше `cli.max_time`; в aaPanel он по умолчанию 100 с |
| `Unknown endpoint: GET /v1/chat/completions` в ответ на POST | nginx завернул свою 502 на `error_page` и вернул запрос в шлюз уже GET-ом; в `public/502.html` лежит ошибка в формате OpenAI — она и должна отдаваться |
| Ответ приходит одним куском, а не словами | на пути включено сжатие или буферизация; проверьте `gzip` для `text/event-stream` |
| Вторая страница не открывается, пока идёт ответ | встроенный сервер PHP в Windows обслуживает один запрос за раз — поставьте nginx |
| Модель «забывает» разговор | клиент не передаёт `X-Session-Id`, и каждый запрос начинает новую беседу |
| `501 ... not available in CLI mode` | эмбеддинги требуют ключ Gemini |
| `cli_no_image` на рисовании | CLI не сохранил картинку: попробуйте другое описание или модель посильнее в `cli.default_model` |
| `update.php` пишет 404 | репозиторий закрыт, нужен ключ: `update.token` или `AGY_UPDATE_TOKEN` |
| Пустые логи | нет прав на запись в `logs/` |
